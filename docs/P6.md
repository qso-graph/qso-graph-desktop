# P6 acceptance registration — personas and services

Registered before any P6 code is written, per `QGD-PRT-0003`. The exit gate is
`QGD-PRT-0106`: KI7MT walks setup on a clean machine, and an export round-trips.
This document lists the tests that will show it; it is not a second copy of the
requirements, which stay in `QGD-SPEC-001`.

P6 depends on P0 and P4, both signed off. P5 is done and awaiting sign-off; P6
needs nothing from it.

## What P6 has to satisfy

`QGD-PSN-0001`–`QGD-PSN-0011`, and the credential core's own rules it runs on —
`QGD-CRD-0002` (the core owns X.509, PKCS#12 and certificate expiry),
`QGD-CRD-0006` (no secret in a log, message or report), `QGD-CRD-0009` (no
secret read at startup or to show status), and `QGD-CRD-0011` (a control that
cannot be used says why without being pressed).

| Test | Required result |
|---|---|
| P6-persona-owns-credential | A credential is stored against a persona and a service. Two personas with the same service hold two separate secrets, and removing one leaves the other (`QGD-PSN-0001`) |
| P6-services-are-data | A service added to the register appears in setup with its own fields, its own secret field and its own test, with no code change. A service removed from the register stops being offered, and a command naming it is refused (`QGD-PSN-0002`, `QGD-PSN-0003`) |
| P6-register-matches-core | Every service the register holds is one the credential core knows how to store for, and every service the core knows is in the register. A register and a core that disagree is the defect this test exists for |
| P6-setup-callsign-only | Guided setup completes with a callsign and nothing else. Every service step can be skipped, and the setup can be left and returned to with what was entered still there (`QGD-PSN-0004`) |
| P6-test-per-credential | Every service in the register either has a test or is marked as having none, and which it is is readable before anything is pressed. A test reports which of the outcomes happened and no test output carries the secret (`QGD-PSN-0005`, `QGD-CRD-0006`, `QGD-CRD-0011`) |
| P6-expiry-from-the-credential | A PKCS#12 certificate's expiry is read from the certificate by the core, not entered by the operator. A certificate near expiry is reported while there is still time; one already expired is reported as expired; one that is not a certificate is reported as unreadable rather than as valid (`QGD-PSN-0006`) |
| P6-export-encrypted | An export is one encrypted file. Nothing in it is readable without the passphrase: the file is searched for every value that went into it, including a planted sentinel, and holds none of them. An export without a passphrase is refused rather than written in the clear (`QGD-PSN-0007`) |
| P6-export-header | The file names its version, its cipher, its KDF, its iteration count and its salt in the clear, and the rest is one authenticated payload. Changing any byte of the payload or the header makes the import refuse it (`QGD-PSN-0008`, `QGD-PSN-0009`) |
| P6-export-round-trip | An export taken on one machine imports onto another with no personas: the personas, their service settings and their secrets are all there, and a credential test passes afterwards with the imported secret (`QGD-PRT-0106`) |
| P6-import-all-or-none | An import into a machine that already has personas says what it would overwrite before it does, and a file that fails its tag changes nothing at all (`QGD-PSN-0009`) |
| P6-import-cannot-tell | A wrong passphrase and an altered file produce the same message, which says it may be either. A run that claims to know which fails (`QGD-PSN-0010`) |
| P6-export-goes-nowhere | Exporting opens no network connection and writes only where the operator chose, asserted the way `QGD-LOG-0012` is for diagnostics (`QGD-PSN-0011`) |
| P6-no-regression | `make verify` stays green end to end, including the twenty-eight suites that exist before P6 starts |

## What is already known, before writing anything

**P1 built the mechanism and none of the rules.** Personas, six providers, save,
test, delete and preference all work and are held by `electron-smoke`,
`credential-editing` and `connection-capture`. What P1 did not do is write down
why: `QGD-PSN-0001`–`QGD-PSN-0011` are new, and the first thing P6 does is make
the six hardcoded provider names into a register that the setup, the tests and
the validation all read.

**The core already answers status without reading a secret.** `QGD-CRD-0009` and
`QGD-CRD-0010` were fixed during P3 — a Keychain prompt at startup was the
symptom. Anything P6 adds has to keep that property, which means an expiry date
cannot be read by decrypting a certificate every time a page is drawn. It is
read when the certificate is saved and kept beside the index, like the other
things the status display answers from.

**Three decisions P6 has to make, recorded here before they are made in code:**

1. **How PKCS#12 is read.** `QGD-CRD-0002` puts X.509 and PKCS#12 in the Rust
   core, and the core's crypto is `aws-lc-rs`, which does no PKCS#12 parsing.
   So this needs either a parsing crate on the credential path — pinned under
   `QGD-SEC-0012` like everything else there — or the expiry read some other
   way. The choice goes in the commit that makes it, with what was weighed.
2. **The KDF's cost.** `QGD-PSN-0008` names PBKDF2-HMAC-SHA-256 and leaves the
   iteration count to be chosen and recorded in the file. It is chosen by
   measuring on the M3, not by copying a number.
3. **What an export contains.** Personas and their service settings, certainly.
   Secrets, because an export whose secrets have to be re-entered is not the
   thing the exit gate asks for. Not the engine's data: that is `QGD-ENG-0011`'s
   backup, a different file with a different purpose.

## Deliberately not in P6

- The app API and grants, which are P7. Personas are frame (`QGD-REP-0003`).
- A user's own Vault as a credential store: `QGD-CRD-0008` keeps the OS
  credential manager the only one in Release 1.
- Moving the engine's data between machines. `QGD-ENG-0011`'s backup already
  does that and is not an export of personas.

## Approach

The register first, because setup, the tests and the validation all read it and
everything else in P6 is shaped by it. Then expiry, because it decides the
PKCS#12 question and that decision reaches the packaging. Then export and
import, which is the exit gate's second half. Guided setup last, because it is
the surface over all of it and it should be built against the thing it drives
rather than ahead of it. Each step keeps `make verify` green rather than ending
with one large reconciliation.

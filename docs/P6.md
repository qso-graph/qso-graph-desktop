# P6 acceptance registration — personas and services

Registered before any P6 code is written, per `QGD-PRT-0003`. The exit gate is
`QGD-PRT-0106`: KI7MT walks setup on a clean machine, and an export round-trips.
This document lists the tests that will show it; it is not a second copy of the
requirements, which stay in `QGD-SPEC-001`.

P6 depends on P0 and P4, both signed off. P5 is done and awaiting sign-off; P6
needs nothing from it.

## What P6 has to satisfy

`QGD-PSN-0001`–`QGD-PSN-0013`, and the credential core's own rules it runs on —
`QGD-CRD-0002` (the core owns X.509, PKCS#12 and certificate expiry),
`QGD-CRD-0006` (no secret in a log, message or report), `QGD-CRD-0009` (no
secret read at startup or to show status), and `QGD-CRD-0011` (a control that
cannot be used says why without being pressed).

| Test | Required result |
|---|---|
| P6-persona-owns-credential | A credential is stored against a persona and a service. Two personas with the same service hold two separate secrets, and removing one leaves the other (`QGD-PSN-0001`) |
| P6-services-are-data | A service added to the register appears in setup with its own fields, its own secret field and its own test, with no code change. A service removed from the register stops being offered, and a command naming it is refused (`QGD-PSN-0002`, `QGD-PSN-0003`) |
| P6-one-list | The register is the only place a service is named. Every service it holds asks only for things the credential core stores, and no second list of service names exists in the code — the contract takes the allowed set from the register rather than holding one (`QGD-PSN-0002`) |
| P6-setup-callsign-only | Guided setup completes with a callsign and nothing else. Every service step can be skipped, and the setup can be left and returned to with what was entered still there (`QGD-PSN-0004`) |
| P6-test-per-credential | Every service in the register either has a test or is marked as having none, and which it is is readable before anything is pressed. A test reports which of the outcomes happened and no test output carries the secret (`QGD-PSN-0005`, `QGD-CRD-0006`, `QGD-CRD-0011`) |
| P6-expiry | Every service in the register answers whether its credential expires and how that would be known. No service claims an expiry this product cannot read, and a register that claims one is refused. The status for a stored credential says *no expiry known* rather than implying it is good indefinitely (`QGD-PSN-0006`) |
| P6-export-encrypted | An export is one encrypted file. Nothing in it is readable without the passphrase: the file is searched for every value that went into it, including a planted sentinel, and holds none of them. An export without a passphrase is refused rather than written in the clear (`QGD-PSN-0007`) |
| P6-export-header | The file names its version, its cipher, its KDF, its iteration count and its salt in the clear, and the rest is one authenticated payload. Changing any byte of the payload or the header makes the import refuse it (`QGD-PSN-0008`, `QGD-PSN-0009`) |
| P6-export-round-trip | An export taken on one machine imports onto another with no personas: the personas, their service settings and their secrets are all there, and a credential test passes afterwards with the imported secret (`QGD-PRT-0106`) |
| P6-import-all-or-none | An import into a machine that already has personas says what it would overwrite before it does, and a file that fails its tag changes nothing at all (`QGD-PSN-0009`) |
| P6-import-cannot-tell | A wrong passphrase and an altered file produce the same message, which says it may be either. A run that claims to know which fails (`QGD-PSN-0010`) |
| P6-export-goes-nowhere | Exporting opens no network connection and writes only where the operator chose, asserted the way `QGD-LOG-0012` is for diagnostics (`QGD-PSN-0011`) |
| P6-no-borrowed-identity | No OAuth or Cognito client belonging to another product appears in the register, the spec or the code, and the credential core declares no AWS, Cognito or SRP dependency (`QGD-PSN-0012`) |
| P6-no-regression | `make verify` stays green end to end, including the twenty-eight suites that exist before P6 starts |

## What is already known, before writing anything

**P1 built the mechanism and none of the rules.** Personas, six providers, save,
test, delete and preference all work and are held by `electron-smoke`,
`credential-editing` and `connection-capture`. What P1 did not do is write down
why: `QGD-PSN-0001`–`QGD-PSN-0011` are new, and the first thing P6 does is make
the six hardcoded provider names into a register that the setup, the tests and
the validation all read.

**The core already answers status without reading a secret.** `QGD-CRD-0009` and
`QGD-CRD-0010` were fixed during P3 — a Keychain prompt at startup was the
symptom. Anything P6 adds has to keep that property. It is why an expiry, if
this product ever holds a credential that has one, is read when the credential
is saved and kept beside the index rather than by opening the secret every time
a page is drawn.

**The credential core names no service.** It takes a provider as an identifier
and stores what it is given, so making the register the one list required no
change in Rust and there is no second list for it to drift from. That is why
`P6-one-list` checks for the absence of a second list rather than comparing two.

**Three decisions P6 has to make, recorded here before they are made in code:**

1. **Whether the product holds ARRL's certificate — already decided, and I
   did not check.** `QGD-PSN-0006` first said the core reads LoTW's PKCS#12.
   It does not, and it never will: **D-9 settles it.** *"TQSL is a required
   install by the user, who sets up their certificates and station locations
   in it... QSO Graph never holds a certificate or manages locations."* The
   LoTW credential kept here is the web account, which carries no date.
   It was raised with KI7MT as an open decision; it was not one, and the
   answer was in the decision record the whole time. The lesson: cite by
   grepping the record, not by recall — and that applies to deciding something is
   undecided.
2. **The KDF's cost.** `QGD-PSN-0008` names PBKDF2-HMAC-SHA-256 and leaves the
   iteration count to be chosen and recorded in the file. It is chosen by
   measuring on an M3 Ultra, not by copying a number.
3. **What an export contains.** Personas and their service settings, certainly.
   Secrets, because an export whose secrets have to be re-entered is not the
   thing the exit gate asks for. Not the stored data: that is backup, deferred under `QGD-ENG-0011`
   (2026-10-10), a different file with a different purpose.

## Where the exit gate stands

`make verify` runs 30 suites, all PASS. Every test registered above has one
behind it:

| Test | Suite |
|---|---|
| P6-persona-owns-credential, P6-export-*, P6-import-* | `persona-export` — 12 checks against the real core and the real Keychain |
| P6-services-are-data, P6-one-list, P6-expiry | `unit` — `tests/services.test.ts`, 20 checks |
| P6-test-per-credential | `credential-editing` — the register and the core held to each other, both ways |
| P6-setup-callsign-only | `setup-walk` — the whole flow in the real application on a clean machine |
| P6-no-borrowed-identity | No OAuth or Cognito client belonging to another product appears in the register, the spec or the code, and the credential core declares no AWS, Cognito or SRP dependency (`QGD-PSN-0012`) |
| P6-no-regression | 30 suites |

What is left is the half of the exit gate that is KI7MT's: walking setup on a
clean machine himself, and taking an export from one machine to another. The
suites show both work; the gate asks him to see it.

Three numbers worth having to hand. An export of two personas and two
credentials is **1,195 bytes**. The KDF is **PBKDF2-HMAC-SHA-256 at 600,000
iterations**, measured at 166 ms on an M3 Ultra. A wrong passphrase and an altered
file give **one message**, which says it may be either.

## Deliberately not in P6

- The app API and grants, which are P7. Personas are frame (`QGD-REP-0003`).
- A user's own Vault as a credential store: `QGD-CRD-0008` keeps the OS
  credential manager the only one in Release 1.
- Moving stored data between machines. That is backup's job (deferred under
  `QGD-ENG-0011`, 2026-10-10), not an export of personas.

## Approach

The register first, because setup, the tests and the validation all read it and
everything else in P6 is shaped by it — done. Then export and import, which is
the exit gate's second half and has no open question in it. Then the per-service
test and the expiry answer, which are both things the register now carries and
the status has to report. Guided setup last, because it is the surface over all
of it and should be built against the thing it drives rather than ahead of it.
Each step keeps `make verify` green rather than ending with one large
reconciliation.

## Open after sign-off

**`setup-walk` has failed twice with a callsign that grew a letter, and has
not been reproduced since.** When it fails, the
persona's callsign has gained one trailing uppercase letter — `W1AW/4S`,
`W1AW/9T` — so the Personas page title does not match what setup was given.
The field holds exactly the right value at the moment the create button is
clicked, proved by instrumenting six consecutive passing runs, so whatever
adds the character is downstream of the form. KI7MT's direction is to treat it as a product bug until proven otherwise, and
it is held that way: the assertion stays exact rather than being loosened,
because a test that tolerates a stray character stops proving what it was
written for.

Thirty-odd runs since have all passed, including under a full `make verify`,
so there is no cause to report yet. What is in place for the next occurrence
is a second assertion immediately after the persona is created, on the status
bar the core's own answer drives. That divides the search in half without
needing someone watching: if it fails there, the core was handed the wrong
callsign; if it passes there and fails at the end, the page grew the letter
afterwards. Both failures happened under load — one inside a full verify run,
one straight after it — so load is the only correlate observed so far.

**A password could be stored that the operator had not entered. Fixed, with a
control; the trigger that exposed it is still unexplained.** `QGD-CRD-0012`.

On 2026-10-09, inside a `make verify` run, `packaged-launch` failed asserting
that only an API key had been saved: `#password-saved` was visible, so a
password had reached the Keychain after the suite emptied that field. KI7MT's
direction was to treat it as a priority security bug rather than a record entry.

**What was ruled out.** Not the work in flight: the run that failed was the
first after `packages/extension-api` and `packages/main/extension-runtime.ts` were added,
and `dist/renderer/app.js` holds no reference to either — the persona surface
was byte-identical to the previous passing run, and no existing file but
`scripts/suites.mjs` had changed.

**Not reproduced.** Twelve runs since have passed, eight of them under eight
busy cores, which is the load the original failure had around it.

**What was established, and it is enough to fix.** The save read the password
field's value at the instant the button was pressed, with blank meaning *keep
what is saved*. That makes the stored secret depend on the field being right at
one moment, so **any** way a value reaches that field without the operator
putting it there writes a secret they did not supply — a stale value, an
autofill, a paste landing late while focus moves. Planting a value through
`.value` with no input event, which is exactly what a person cannot do and
everything else can, reproduces the original symptom **deterministically** and
character for character: `#password-saved` expected hidden, received visible.
That does not prove the original trigger, but it does show the original symptom
needs nothing more exotic than a value arriving without an input event.

**The fix does not depend on knowing the trigger.** Intent is now read from the
operator's own `input` events rather than from the field's value, so a field
nobody typed into sends nothing whatever it contains. Blank still means keep,
and `Remove` is still how a secret is deleted; untouched now means the same as
blank.

The control is in `scripts/smoke.mjs` and it fails on the application as it was
— verified by rebuilding without the fix — with a control-for-the-control that
types the same value and requires it to be saved, so the check cannot pass on an
application that has merely stopped saving passwords. Its first version was
worthless and said so: it asserted the indicator straight after the click and
passed against the unfixed code, because it read the indicator before the save
round-trip returned. The completion signal is now the status line the save
itself writes.

**The focus-race hypothesis (2026-10-09), against both intermittents.** Its
reading — keystrokes meant for the next field landing in the previous one
because focus moved late — fits this one's neighbourhood: the suite works the
clipboard with real `Meta+a`/`Meta+c`/`Meta+v` keystrokes while focus moves
between Password and API key, and that is the sort of thing that puts a value
in a field nobody typed into. It does **not** fit the callsign walk, which
sends no keystrokes at all after the callsign and fills every field by locator
— which is the test-side mitigation he recommended, already in place. His
product-side suggestion, that the input must not stay focused and editable once
Create is pressed, is already structurally true for setup: the callsign input
leaves the DOM when the step advances.

**The two are still not filed as one defect.** What they share is the frame
KI7MT put on them — a field's value wrong at the moment it is used, under load
— and that frame is what produced this fix. What they do not share is a
mechanism: this one is now closed by construction, and the callsign's value was
already wrong *before* the core was called, with the field itself proven
correct at the click. One explanation accounting for both would have to be
found, not assumed.

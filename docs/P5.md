# P5 acceptance registration — reference data

Registered before any P5 code is written, per `QGD-PRT-0003`. The exit gate is
`QGD-PRT-0105`: the reference data loads into the engine, and the validation
built from it answers ADIF's own cases. This document lists the tests that will
show it; it is not a second copy of the requirements, which stay in
`QGD-SPEC-001`.

P5 depends on P4, which is signed off.

## What P5 has to satisfy

`QGD-REF-0001`–`QGD-REF-0016`, and the engine requirements it runs on —
`QGD-ENG-0001` (reference data is frame, in its own schema), `QGD-ENG-0010`
(an application reaches it through a role, not by owning it) and
`QGD-ENG-0013` (its tables arrive by migration like everything else).

| Test | Required result |
|---|---|
| P5-archive | ADIF's resources archive is fetched at the pinned version and verified by SHA-256 before anything is read out of it; a changed archive is refused rather than loaded (`QGD-REF-0003`) |
| P5-structure | What is loaded is ADIF's own structure: every data type, every enumeration and every one of the 186 fields, counted against the archive rather than against a list in this repository — including the two fields whose published data type cell names two types (`QGD-REF-0004`, `QGD-REF-0011`) |
| P5-provenance | Every list carries its owner and its source as two separate facts, with version, date and checksum. A list whose owner is unrecorded fails the run (`QGD-REF-0002`) |
| P5-zones | CQ and ITU zones are derived from `Primary_Administrative_Subdivision` and recorded as derived, with CQ Magazine and the ITU named as the authorities and ADIF named as the copy (`QGD-REF-0007`) |
| P5-zone-coverage | What the derivation yields stays plainly short of CQ's 40 zones and the ITU's 90, and how far it reaches is measured from the archive. A run that produced all 40 would mean this product had written CQ's list by hand (`QGD-REF-0015`) |
| P5-uninterpreted | Every zone cell the derivation cannot read is stored exactly as published and flagged, counted from the archive rather than against a number written here. Nothing is derived from one (`QGD-REF-0011`, `QGD-REF-0015`) |
| P5-not-loaded | A first run with no network reaches a migrated, running engine whose reference data is reported *not loaded*. The engine is not stopped, the state is in the database, and it is said once in the log (`QGD-REF-0014`) |
| P5-loads | The data is in the engine, in the frame's schema, after a migration — not in a file beside it, and not compiled in (`QGD-REF-0001`) |
| P5-validation-is-data | Validation answers from the loaded data: a value accepted for a mode is one ADIF lists, and a mode added to the data is accepted without a code change (`QGD-REF-0005`) |
| P5-unsupplied-enumeration | `DARC_DOK` and `MY_DARC_DOK` are reported as *not checked against a list*, which is neither a pass nor a failure. A run that records either as valid, or as invalid, fails (`QGD-REF-0006`) |
| P5-adif-cases | ADIF's own 6,197 test QSOs are read and validated against the rules read back out of PostgreSQL. Every disagreement is listed and the run fails on any of them (`QGD-REF-0008`) |
| P5-coverage | A value outside what a list covers is reported as *not checked*, and a value inside its coverage that the list does not hold is still invalid. Without the second, the first is a way of passing everything (`QGD-REF-0016`) |
| P5-pota-sources | The three POTA sources are fetched live by `make setup` and their shape checked with the product's own readers: the park CSV's header and columns, and the fields of a program and a location. All three load into the engine, and nothing of POTA's is in the repository or in a release (`QGD-REF-0009`) |
| P5-pota-freshness | A load records its URL, ETag, Last-Modified, fetch time and row count; a second load within the day asks conditionally and does not replace anything; a fetch that fails, or arrives with the wrong shape, leaves the previous load in place (`QGD-REF-0010`) |
| P5-pota-unaltered | The four parks with impossible coordinates are stored with exactly the values POTA publishes, flagged, excluded from anything that measures or maps, and still found by reference. Retired parks are present. The test park is flagged and absent from user-facing results (`QGD-REF-0011`) |
| P5-pota-entities | A park whose POTA entity number is not an ADIF DXCC code is loaded with its number intact and no ADIF link, rather than refused. The 113 parks in POTA's own 13 entities are all present (`QGD-REF-0012`) |
| P5-pota-locations | A park published with several locations has a row per location, and one published with none still loads (`QGD-REF-0013`) |
| P5-no-regression | `make verify` stays green end to end, including the twenty-five suites that exist before P5 starts |

## What is already known, before writing anything

**ADIF reproduces lists it does not own, and twice it names one it does not
ship at all.** `DARC_DOK` and `MY_DARC_DOK` are typed `Enumeration`, and ADIF's
own note is that DARC publishes two lists — neither of which is in the archive.
A validator built from ADIF alone cannot check a DOK against anything, and must
say so rather than quietly passing every value or failing every value.

**CQ and ITU zones are not lists in ADIF either.** They appear as two columns on
`Primary_Administrative_Subdivision`, 1,965 rows of them. The zones themselves
are CQ Magazine's and the ITU's. Anything this product derives from those
columns is a derivation from a copy, and is recorded as one.

Both are the same rule — the owner of a list is its authority, and ADIF is a
copy of what it reproduces — which is why `QGD-REF-0002` asks for the owner and
the source as separate facts rather than one field called "source".

## What POTA's data turned out to be

Profiled against a live fetch on 2026-10-08, which is also how the numbers in
`QGD-REF-0010` to `QGD-REF-0013` were arrived at: 96,412 parks, 249 programs,
4,006 locations. 92,118 parks active and 4,294 retired; 2,203 with no entity;
1,618 in more than one location; 57 with no coordinates at all and four with
coordinates that cannot exist; 14,972 names that are not ASCII.

Two things were not as described and are worth saying plainly, because both
would have been found by the loader failing rather than by reading:

- **`entityId` is POTA's own numbering.** It agrees with ADIF's DXCC codes for
  298 of the 311 entity numbers in the park list and disagrees for 13 — the
  same places under different numbers, including India twice. `QGD-REF-0012`
  is written from that.
- **`HEAD` on `api.pota.app/programs` is refused with 403 while `GET` returns
  200.** A freshness check that asks with `HEAD` would conclude the programs
  endpoint is gone.

## What ADIF's own data turned out to be

Measured against the pinned archive while building the load, not read off its
documentation. Each of these changed a decision:

- **Two of the 186 fields publish two data type names in one cell.**
  `CREDIT_SUBMITTED` and `CREDIT_GRANTED` are typed `CreditList,AwardList`,
  and no data type is named that. A foreign key from the field to its data
  type would have refused both fields — the same shape as `QGD-REF-0012` in
  POTA's entity numbers, found in ADIF's own export. The cell is stored as
  published and the resolution recorded beside it.
- **The zone columns are filled for 152 of 1,965 subdivisions**, across five
  DXCC entities (Canada, the two Russias, Kaliningrad, the USA). So a zone
  list derived from them holds 11 of CQ's 40 and 22 of the ITU's 90. It is a
  coverage list, and a zone cannot be validated against it; `QGD-REF-0015` is
  written from that.
- **Three of those cells are not zone numbers**: `S=16 T=17` in a CQ column,
  `07/08` and `06/07` in ITU columns, across 13 subdivisions. The first
  version of the derivation dropped all three silently, because the obvious
  guard — split on commas, keep what is numeric — discards anything else
  without a word. They are now stored as published and flagged uninterpreted,
  and nothing guesses at the notation.
- **ADIF already has POTA data types.** `POTARef` and `POTARefList` are two of
  its 28 types, which is where the POTA reference data and the ADIF
  definitions meet.
- **The second column of the header is the enumeration's value column**, in
  all 25 of them. The archive's key is not always the value: `Mode` is keyed
  by `AM`, but `Region` is keyed `IV.206` — the region code and the DXCC
  entity joined. A validator looking values up by key called nine of ADIF's
  own test QSOs invalid. The value column is now read off the header, so a
  26th enumeration needs no edit, and a header that is not that shape is
  refused rather than guessed at.
- **`Secondary_Administrative_Subdivision` holds 58 rows, every one in
  Alaska.** `CNTY` is typed against it for every DXCC entity, and
  `USACA_COUNTIES`'s own documented example is `MA,Franklin:MA,Hampshire` —
  three Massachusetts counties appear in ADIF's test QSOs and the list has
  none of them. `QGD-REF-0016` comes from this: a list that does not cover a
  value cannot judge it. The whole six remaining disagreements were this one
  fact.
- **`SponsoredAwardList` names an enumeration ADIF does not ship.** Its own
  description is "a comma-delimited list of members of the `Sponsored_Award`
  enumeration", and there is no `Sponsored_Award` among the 25. That is a
  second instance of `QGD-REF-0006`'s case, found by building the validator
  rather than by reading — the first was `DARC_DOK`.

## What POTA's load turned out to need

- **The park list with coordinates is `all_parks_ext.csv`**, not
  `all_parks.csv`: the shorter one has five columns and no coordinates at all.
  Both are published; only the longer one answers the questions `QGD-REF-0011`
  is about.
- **Only the park list offers a validator.** It answers with both an `ETag` and
  a `Last-Modified`, and a conditional ask gets a 304. `api.pota.app/programs`
  and `api.pota.app/locations` offer neither, so for those two the daily limit
  is the whole of what prevents a refetch — recorded as null rather than
  invented.
- **`Number(null)` is 0, and 0 is a DXCC entity code.** A location POTA
  publishes with no entity was being stored as being in entity 0, which is
  ADIF's "None" and a different claim from "POTA does not say". Caught by a
  unit test written for exactly that row.
- **A park's locations are a quoted comma-separated field**, which is why the
  CSV reader is written out rather than taken from a split: a split on commas
  turns one park in three locations into a row with ten columns.

## Where the exit gate stands

`make verify` runs `adif-validation`, which loads the definitions into a real
engine, reads the rules back out of PostgreSQL and validates all 6,197 of
ADIF's test QSOs with them: **54,212 values valid, 16 not checked against a
list, 0 disagreements.** Each of the 16 is one of four causes, every one a fact
about ADIF's archive rather than a gap here, and the suite fails on a
seventeenth that nobody accounted for.

It also runs `pota-load`, which loads POTA's three lists into the engine:
**96,412 parks, 249 programs, 4,006 locations and 96,638 park-location rows**;
4 parks with impossible coordinates stored as published and flagged; 4,294
retired parks kept; 1 test park flagged; and 113 parks in the 13 POTA entity
numbers that are not ADIF DXCC codes, all loaded with no ADIF link while 94,096
are linked. A failed fetch, a malformed list and a truncated one each keep the
last good data, and a list that really changed is loaded — the last of those
being the control, without which a loader that refused everything would pass.

## Deliberately not in P5

- QSO storage. P5 loads the definitions and the validation built from them;
  `QGD-PRT-0108` keeps QG ADIF to files only.
- The app API and grants, which are P7. P5's data is frame, reached through the
  engine's roles.
- DOK and Special DOK lists from DARC. Fetching a second authority's list is a
  decision about a new source with its own provenance, and nothing in P5's exit
  gate needs it — `QGD-REF-0006` is what makes their absence visible instead of
  silent.

## Approach

The archive first, pinned and verified, because everything else is read out of
it. Then the schema and the load, so the data is in the engine before anything
is built on it. Then the validation, from the data. Then ADIF's own test QSOs,
which is the exit gate and the thing most likely to find the gap between what
the definitions say and what a validator does with them. Each step keeps
`make verify` green rather than ending with one large reconciliation.
